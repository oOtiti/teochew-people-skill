# Teochew People 自进化 LLM Wiki 设计

**状态：** 已确认设计，实施计划已完成

**日期：** 2026-08-14

**目标版本：** `teochew-people-skill` 下一次功能版本

## 1. 目标

把现有的潮汕文化写作参考资料升级为一个完整、可追溯、会持续演进并支持本地个性化的 LLM Wiki skill。

系统必须同时做到：

- 让 AI 能快速定位潮汕文化主题，而不是每次重新拼接零散资料。
- 让事实能够回溯到原始来源，并保留地域、时间和适用范围。
- 为文章、口播、短视频脚本、分镜和文化类视频生产提供可核验的场景细节。
- 遇到不清楚、存在争议或具有时效性的内容时，主动研究并更新知识。
- 将公共知识、用户个性化知识和项目上下文分层保存。
- 保持对信俗、宗族、性别、地方差异和当代变化的客观表达。
- 用统一、克制、具有史诗感的视觉重新呈现项目。
- 在项目页展示由 Wiki 实际生成并经过核验的文章、视频脚本和图片效果。

本设计采用 Andrej Karpathy 提出的 LLM Wiki 核心模式：原始资料保留在知识页之外，LLM 持续维护结构化主题页，使知识在查询前完成整理并逐步积累。

## 2. 非目标

- 不把项目做成宗教仪轨、风水、择日或家族规矩操作手册。
- 不自动把单个村落、家庭或个人经验推广为整个潮汕文化事实。
- 不整篇复制受版权保护的新闻、书籍或论文。
- 不默认上传、提交或发布用户的个人背景和家庭信息。
- 不在本次升级中引入向量数据库、托管服务或必须配置 API Key 的运行时。
- 不用单条热点新闻永久改写稳定的历史或文化结论。

## 3. 产品原则

### 3.1 原始资料与主题知识分离

`raw/` 保存不可随意改写的来源记录；`wiki/` 保存由多个来源综合形成、面向查询与写作的主题知识页。

用户界面和 README 不使用“编译内容”作为产品术语。对使用者只描述“原始资料”“主题知识页”“持续演进”和“来源追踪”。

### 3.2 证据、推断与未知分离

每个重要判断必须能够归入以下状态之一：

- **已证实：** 有明确来源直接支持。
- **综合判断：** 由多个事实合理归纳，但不是来源原文结论。
- **存在差异：** 不同地区、家庭、年代或来源给出不同做法。
- **尚不清楚：** 当前资料不足，回答时应说明并继续研究。

### 3.3 稳定知识与热点事件分离

长期主题页负责定义、历史脉络、地方差异和稳定事实。热点事件页必须带发生时间、报道时间和最后核验时间，并链接回长期主题。

### 3.4 个性化只在本地演进

公共仓库提供共享核心知识。用户画像、偏好、地区背景和项目上下文默认写入独立本地 vault，不因 npm 更新而丢失，也不会自动进入公共仓库。

### 3.5 先精选输入，再整理知识

搜索结果只是候选资料，不是知识。候选来源必须经过来源准入评估，检查权威性、是否直接支持主张、地域适配、时效、独立性和利益偏向。只有通过评估的来源才进入公共 raw 语料；被拒绝或仅供线索使用的来源记录选择理由，但不能被主题页当成事实依据。

## 5. 页面模型

### 5.1 原始资料记录

每个 `raw/YYYY-MM-DD/<source-id>.md` 包含：

```yaml
---
id: gd-dfz-chaozhou-dialect-2024
title: 潮州方言及其特点
publisher: 广东省情网
source_type: government
url: https://example.com/source
published_at: 2024-01-01
accessed_at: 2026-08-14
regions: [汕头, 潮州, 揭阳, 海外潮人社群]
topics: [潮汕话, 范围与称谓]
authority: high
quality_tier: A
claim_roles: [definition, geographic_scope, visual_detail, sound_detail]
language: zh-CN
status: active
---
```

正文只保存：

- 来源内容摘要。
- 可由该来源直接支持的事实。
- 地域和时间限制。
- 必要的短引文及其位置。
- 与其他来源的冲突或互补关系。
- 来源失效时的存档或替代来源说明。

抓取到的正文不能未经许可整篇提交。来源记录一旦进入索引，只允许追加更正说明，不静默改写既有事实摘要。

来源质量分为：

- **A：核心依据。** 政府、方志、档案、学术原始研究、博物馆或项目官方材料，且能够直接支持对应主张。
- **B：可靠补充。** 具备采访、编辑和事实核查机制的机构或媒体材料，用于补充背景、当代变化和具体案例。
- **C：情境材料。** 社区讲述、地方实践记录和个人经验，只能说明某时某地的生活经验，不能证明普遍性。
- **Reject：不准入。** 无出处转载、营销号、互相抄袭页面、无法确认作者和时间的资料，或与主张没有直接关系的来源。

稳定的核心事实至少需要一条 A 级来源，或两条相互独立且直接支持主张的 B 级来源。争议性判断需要主动寻找反例或不同观点。C 级来源不得单独支撑定义、起源、普遍范围和官方认定。

`raw/source-review.md` 追加记录搜索角度、候选来源、准入结果和理由。raw 索引只收录通过准入的来源。

### 5.2 主题知识页

每个主题页包含：

```yaml
---
id: custom-bai-laoye
title: 拜老爷
aliases: [拜神, 敬神]
page_type: custom
regions: [潮汕文化圈]
knowledge_status: reviewed
freshness: enduring
last_verified: 2026-08-14
source_ids: []
related: [营老爷, 地方神明, 家庭礼俗]
---
```

正文使用统一结构：

1. 一句话定义。
2. 已确认事实。
3. 地方、家庭和年代差异。
4. 与相近概念的区别。
5. 历史与当代变化。
6. 适合如何表达。
7. 不应如何概括。
8. 尚不清楚或需要实时核验的内容。
9. 可用于写作与视频生产的场景细节，包括人物、动作、器物、声音、空间和时间顺序。
10. 生产使用边界：哪些细节可直接使用，哪些只能作为地方个案，哪些需要再次核验。
11. 相关页面与来源。

### 5.3 热点事件页

热点页增加：

- `event_date`
- `reported_at`
- `last_checked`
- `event_status`
- `linked_topics`
- `supersedes` / `superseded_by`

事件页只记录当时发生了什么、有哪些可靠来源、它与长期主题有什么关系。对趋势的判断必须明确标记为综合判断。

## 6. 运行操作

### 6.1 Ingest

1. 接收 URL、文件、文字或用户提供的材料。
2. 判断来源类型、可信度、地域和时间范围。
3. 检查是否已经收录或存在同源副本。
4. 写入新的 raw 记录。
5. 更新 raw 索引和 wiki log。
6. 不在 ingest 阶段直接把单一来源当成完整主题结论。

### 6.2 Research

1. 把问题拆成定义、历史、地域差异、相反证据和当代变化。
2. 优先查政府、方志、博物馆、学术机构和项目官方资料。
3. 对核心或争议判断寻找独立来源与反例。
4. 在准确性优先的前提下，评估来源是否提供可用于写作和视频的具体场景、动作、器物、声音、空间与人物关系。
5. 保存选中的来源记录。
6. 按 A/B/C/Reject 完成来源准入评估，并记录未采用资料的原因。
7. 更新或创建主题页，并标记证据状态及内容生产用途。
8. 记录研究日期、未解决问题和下一次复核条件。

### 6.3 Query

1. 先通过 `wiki/index.md` 选择一至三个最相关页面。
2. 需要核对细节时回溯 raw 来源。
3. 如果页面陈旧、相互冲突或无法覆盖问题，则进入 research。
4. 输出中保留地方差异、事实与推断边界。
5. 对“最新、当前、官方认定、活动安排、人物状态”等内容实时核验。

### 6.4 Evolve

查询或研究产生可复用的新认识时：

1. 判断它属于公共事实、个人偏好还是项目上下文。
2. 公共事实只能在有来源后更新公共主题页。
3. 个性化信息写入本地 vault。
4. 项目信息写入项目 overlay。
5. 更新相关链接、索引和 wiki log。
6. 不因一次回答风格偏好改变公共事实层。

### 6.5 Lint

自动检查：

- raw 和 wiki 索引是否覆盖实际文件。
- 页面 ID、别名和内部链接是否唯一有效。
- 主题页列出的 source ID 是否存在。
- 热点页是否超过复核期限。
- 官方认定、活动时间和人物信息是否需要实时复核。
- 是否出现没有地域限定的“潮汕人都”“必须”“一定”。
- 是否把拜老爷、营老爷、祭祖、宗族礼俗等相近概念混写。
- 是否存在没有入站链接的孤立页面。
- 是否存在同一事实的互相冲突版本。
- 主题页的核心事实是否达到来源准入门槛。
- C 级情境材料是否被错误用于证明普遍性、起源或官方状态。

安全的索引和链接问题可自动修复；内容冲突只报告，不自动选择结论。

## 7. 自进化与个性化

### 7.1 三层知识

```text
公共核心 skill wiki
        ↓
用户全局 vault：~/.teochew-people/
        ↓
项目 overlay：<project>/.teochew-people/
```

查询时按“项目 overlay → 用户 vault → 公共核心”合并。上层可以补充背景和表达偏好，但不能伪造或覆盖公共事实。

### 7.2 可以学习的内容

- 用户明确说明的地域背景。
- 常用中文、英文或双语表达方式。
- 喜欢的文体、长度、语气和目标受众。
- 用户明确提供的家庭称谓或本家做法，并标为私人经验。
- 已确认的项目术语、品牌口径和受众要求。

### 7.3 不自动学习的内容

- 宗教信仰、政治立场、健康情况等敏感推断。
- 从姓名、口音或地名猜测出的身份。
- 未经用户确认的家庭或村落规则。
- 来自公共聊天但用户没有要求持久保存的信息。

### 7.4 安装与升级

安装器新增 vault 初始化能力。skill 更新只替换公共核心，不覆盖用户 vault。项目 overlay 默认加入推荐 `.gitignore`，是否提交由用户决定。

## 10. 视觉系统

### 10.1 核心方向

视觉只在英雄图上使用一次强烈的史诗感，其余 README 保持安静、清楚、易读。

背景表现潮汕山海、潮水、古厝屋脊、远方灯火和跨海往返的空间感。避免把神像、祭祀器具或某一城市地标作为整个潮汕的唯一象征。

### 10.2 英雄图

英雄图前景只出现一行大字：

```text
TEOCHEW PEOPLE
```

不得再加入中文标题、口号、功能标签、按钮、图标或说明文字。

实现方式：

- 使用图像生成工具制作无文字的 16:9 史诗背景。
- 使用 SVG 确定性叠加 `TEOCHEW PEOPLE`，保证拼写和排版准确。
- 从相同构图导出 README hero 与 GitHub social preview，保持品牌一致。
- 保留充足暗部或负空间，让大字在缩略图中仍清楚。

建议色彩：

- 深潮蓝 `#081820`
- 夜海青 `#12323A`
- 矿物朱红 `#9E2B22`
- 灯火金 `#D7A85B`
- 盐白 `#F2EEE4`

### 10.3 README

英雄图下方重新组织全部介绍：

1. 一句话说明它是什么。
2. 为什么是 LLM Wiki，而不是普通资料合集。
3. 查询、研究、演进和个性化如何工作。
4. 它如何帮助文章、口播、短视频、分镜和文化内容审校。
5. 内容范围与客观性原则。
6. 安装与初始化。
7. 常见使用方式。
8. raw、wiki 和本地 vault 的结构。
9. 如何贡献来源和主题页。
10. 校验、版本和许可证。

移除当前英雄图中重复出现的卖点、标签和装饰性文案。动态案例图同步改为新视觉，但仍以清楚展示能力差异为首要目标。

## 11. 校验与测试

### 11.1 行为基线

修改前使用以下类型提示验证现有 skill 的缺口：

- “拜老爷和营老爷是一回事吗？”
- “潮汕人一般拜哪些老爷？”
- “最近潮汕有什么文化热点？”
- “按我揭阳家庭的习惯改写，但不要当成全潮汕统一做法。”
- “这个非遗项目现在还是国家级吗？”

记录无法找到来源、概念混淆、时效缺失和个性化无法持续等失败表现。

### 11.2 自动校验

`npm test` 最终覆盖：

- skill frontmatter 与 Agent Skills 结构。
- raw 和 wiki 元数据 schema。
- 索引完整性、内部链接和 source ID。
- 热点时效与需要实时核验的字段。
- 安装器、用户 vault 初始化和升级不覆盖。
- README、hero、social preview 和 npm 打包清单。
- `npm pack --dry-run` 不遗漏公共核心文件，也不包含个人 vault。

### 11.3 行为复测

使用与基线相同的提示重新调用 skill，确认：

- 能定位正确主题页。
- 能区分拜老爷和营老爷。
- 能回溯来源并说明不确定性。
- 能识别需要实时查询的信息。
- 能应用用户偏好而不改变公共事实。

### 11.4 视觉验证

- README 桌面宽度与移动缩放检查。
- Hero 标题拼写、对比度、留白和缩略图可读性检查。
- social preview 裁切检查。
- 动态案例图与新视觉的一致性检查。

## 12. 发布与准出

本次工作在独立分支完成。实现、资料准入、行为测试、示例文章与视频、视觉检查、安装测试和打包检查全部通过后：

1. 推送 GitHub 分支并创建 PR。
2. 通过 GitHub 检查后合入默认分支。
3. 在默认分支复验完整测试和 npm 包内容。
4. 发布 `teochew-people-skill@0.2.0` 到 NPM，并从公开 registry 回查版本与文件。
5. 更新 GitHub Issue #1，列出拜老爷主题页、精选来源、验证方式、示例产物和发布版本；确认问题已解决后关闭。

README 同时作为 GitHub 与 NPM 项目页，必须直接展示英雄图、来源驱动的示例文章、短视频口播/分镜效果和前后对比，而不能只描述能力。

## 13. 验收标准
